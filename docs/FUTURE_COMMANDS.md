# Future planned command proposals

This is a roadmap, not a list of commands available in the current executable.
Use `pkmn get-all-cmds` or [ALL_COMMANDS.md](ALL_COMMANDS.md) for commands that
the current build advertises. Proposed syntax may change before implementation.

## Japanese Gen I → international Gen I

Add Japanese Red and Green source profiles and conversion workflows that can
map their save semantics into an international Pokémon Red or Blue save. This
is a separate feature from the existing experimental Japanese Red → FireRed
bridge.

Proposed command shape:

```text
pkmn red-jp convert-gen1 <save.sav> --profile JP_RED_REV0|JP_RED_REV1 \
  --target red|blue [--output <target.sav>] [--output-json <target.red.json>]

pkmn green-jp convert-gen1 <save.sav> --profile JP_GREEN_REV0 \
  --target red|blue [--output <target.sav>] [--output-json <target.red.json>]
```

The exact supported Green revisions/profiles and option names must follow the
version evidence in the implementation. Do not infer a revision from the save
unless the save format provides a verified discriminator.

### Japanese-text preservation contract

“Preserve Japanese text” must be precise about which artifact retains it:

- The translated English-shaped Gen I JSON must preserve the original Japanese
  names alongside the English-compatible semantic names. Store the exact
  original name bytes, decoded Unicode text, padding/terminator information,
  and ambiguous-glyph provenance for every supported name field in a clearly
  separated source-provenance extension. A source archive may also be emitted
  for full archival reconstruction, but it is not the only place the JSON
  keeps Japanese name provenance.
- International English Gen I Red/Blue use a different text character map and
  cannot natively display Japanese glyphs. The generated English `.sav`
  therefore cannot be advertised as containing displayable, losslessly
  preserved Japanese text.
- Until an English Gen I runtime/ROM patch with Japanese text support is
  explicitly in scope and verified, the converter must apply a visible,
  user-selectable policy for target-compatible names (for example, retain an
  available English alias or use a documented fallback) and report each
  transformed/unrepresentable name.
- Save generation from the translated JSON must read only the English semantic
  name fields. Japanese source-provenance fields are archival/annotation data,
  are not generation authority, and must not change generated bytes when
  modified. Preserve the originals in the JSON even though the English save
  uses English-compatible names.
- If a separate source archive is emitted, keep it associated with the outputs
  and include its hash/reference in the conversion manifest when manifests are
  implemented.
- If the requested meaning is that Japanese glyphs remain visible in the
  resulting English Red/Blue game itself, the route must be marked unsupported
  until a compatible target runtime/patch is separately designed and tested.

### Planned conversion behavior

- Accept Japanese Red and Japanese Green only after their layouts, text codecs,
  checksums, and supported source revisions have explicit profiles.
- Let the user choose international Red or Blue as the target, subject to a
  verified semantic mapping. Report version-specific encounter/progression
  differences rather than silently inventing game history.
- Decode source names to glyphs and provenance first; keep Japanese originals
  in the translated JSON's provenance fields and never copy Japanese raw bytes
  into English semantic name fields.
- Map supported semantic state into the target Gen I layout, reconcile the
  selected-box cache, and regenerate target checksums.
- Refuse unsupported/corrupt source layouts and unsupported semantic state
  rather than producing a misleading save.
- Write the converted `.sav` and Japanese archive as separate, collision-safe
  outputs. Never overwrite the source save or silently overwrite either
  output.
- Validate and re-decode the generated target, compare supported non-text
  semantics, and produce a report listing preserved, translated, normalized,
  omitted, and unsupported fields.
- Add synthetic/public fixtures and tests for each revision, both target games,
  Japanese name aliases, target-name policy, checksum validity, cache handling,
  output collisions, determinism, and archive recovery.
- Require real-save and emulator acceptance before describing the route as
  game-verified.

## Cross-game conversion planning and verification

Make conversion behavior easier to preview, audit, and troubleshoot before and
after writing the target save.

Proposed commands/options:

```text
pkmn convert plan <route> <source> [conversion options]
pkmn convert <route> <source> [output] [--dry-run] [conversion options]
pkmn verify-conversion <source> <target> [--manifest <file>]
pkmn convert explain <route> <field>
```

`convert plan` and `--dry-run` should report source/target profiles, evidence
status, output names, field mapping summary, warnings, and unsupported state,
without writing save outputs. `verify-conversion` should validate target
checksums/container, inspect a manifest when supplied, and compare the
supported mapped semantics. Extend the existing `convert explain` field set
with supported Pokémon/name/badge/progress decisions; do not duplicate the
existing command under a new name.

## Profile discovery

Offer profile discovery as a confidence-bearing diagnostic, not an authority
that silently selects a profile when layouts or revisions are ambiguous.

```text
pkmn identify <save.sav> [--format text|json]
pkmn profiles [--format text|json]
```

`identify` should report candidate game/region/revision profiles, evidence,
confidence, and what confirmation is needed. It must not use ROM contents or
claim an exact revision if the save cannot prove one. `profiles` lists source
and target support status and evidence level.

## JSON name and provenance inspection

Provide ways to understand what source text and semantic history a JSON file
retains, especially for Japanese-to-English Gen I projection:

```text
pkmn json names <file.json> [--format text|json]
pkmn json provenance <file.json> [--format text|json]
pkmn json export-report <file.json> [--format text|json|markdown]
```

For Japanese-origin documents, `json names` should show the original Japanese
glyphs/bytes and provenance separately from the English-compatible semantic
names used to generate an international Gen I save. Save generation must use
only the English-compatible fields for that target. The Japanese text remains
in the JSON for reference/recovery; the English save is not claimed to display
Japanese names. `provenance` should show source profile, mapping decisions,
transformations, and omissions. `export-report` previews what a target save
will retain, translate, normalize, omit, or reject.

## Unified batch workflows

Add consistent cross-game batch entry points while retaining existing
game-specific commands:

```text
pkmn validate-batch <save.sav>...
pkmn convert batch <source.sav|source.json>... --route <route> \
  --output-dir <directory> [--dry-run]
pkmn batch report <directory> [--format text|json|markdown]
```

Batch preflight should identify every input, target, warning, and proposed
output before writing. The result report must distinguish successes, skips,
and failures per input; transactional workflows must not leave a partial
result presented as a complete batch. A unified validator dispatches only to
formats with an unambiguous or user-confirmed profile.

## JSON comparison and save overview

```text
pkmn json diff <a.json> <b.json> [--include-physical-image]
pkmn save info <file.sav|file.json> [--format text|json|markdown]
```

`json diff` should compare semantic fields and ignore archival physical-image
data by default, reporting whether excluded data differed. `save info` should
dispatch to a supported profile and provide one concise overview; ambiguous
inputs require user selection rather than a guess.

## Output discovery, health check, and interactive search

```text
pkmn outputs list <directory> [--format text|json]
pkmn self-test [--format text|json]
pkmn interactive --search <term>
```

`outputs list` should recognize documented `pkmn` reports, manifests, and
generated saves without opening or modifying them. `self-test` should be a
short installed-build health check, clearly distinguished from the deeper
`doctor --deep` test. The guided command browser and coverage registry are
already implemented inside `pkmn interactive`; its `S` control searches the
current catalog. `interactive --search <term>` remains a proposed direct-entry
shortcut for opening that browser with a filter already applied.

## Suggested implementation order

1. Japanese Gen I → international Gen I with English generation fields,
   Japanese-origin JSON name provenance, and physical-image isolation.
2. Conversion planning/dry-run and post-conversion verification.
3. Profile discovery and a support-status listing.
4. JSON name/provenance/export reports.
5. Unified batch preflight and reports.
6. JSON diff and concise cross-game save info.
7. Output discovery, short self-test, and interactive search.

All entries in this document remain proposals until implemented, tested, and
added to the active catalog. Syntax and ordering may change as the command
router and supported format registry evolve.
